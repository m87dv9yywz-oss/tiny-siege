# Tiny Siege v3: Kingdom Adventure

V2.0.1 is recoverable at tag `v2.0.1` (`4aac36c`). Classic preserves its original 20 waves, five towers and all 15 evolutions without permanent gating or progression rewards. GitHub Pages and `/tiny-siege/` remain the hosting/base. Phaser 4.2.1, Vite 8.3.4 and Canvas rendering remain pinned.

## Progression and balance

Battle gold resets to 300 and lives to 20. Crowns and XP are per-profile permanent resources. Archer/Cannon/Frost start available; Fire costs 75 Crowns and Lightning 130. Tier 1 paths are available immediately. Each path's Tier 2 unlock costs 180 class XP and Tier 3 costs 500 more; actual battle purchases still use the v2 gold prices and 3-1-0 restrictions.

Emerald Beginner has 14 waves, Amber and Moon have 20. First clears reward 100/120/150 Crowns; repeats reward 35/45/55. Failed attempts give meaningful-use XP, but no Crowns, avoiding Crown retry farming. Stars: 18+ lives = 3, 10+ = 2, otherwise 1. Tower XP includes damage, armor destruction, Frost control and tower participation. Each class earns at most 350 XP per run. Wave checkpoints save increments and the final reward is idempotent, including after reconnect. Two strong runs can earn enough for a first ultimate unlock; lightly used classes take longer.

`node scripts/v3-balance-report.js` simulates legal positions and purchases using only earned gold and permanent rewards from previous runs. It writes detailed wave lives, earned/spent gold, tower paths, escapes, durations, profile state and XP to `docs/v3-balance-results.json`. It requires safe first three waves and a successful earned progression route. The report covers starter-only Beginner (20 lives), Tier-2 starter Amber (11), earned starter-ultimate Moon (20), then mixed, physical and control builds using their owned specializations. The simulator chooses good bend coverage; these results establish viability, not a claim that every novice or specialization wins. An unprepared magic-heavy build without unlocked physical counters can fail against the King. The unchanged Classic regression also covers five earned-gold strategies.

## Profiles, saves and privacy

Startup lets players create/select nicknames and predefined fantasy avatars. Profiles isolate currencies, XP, unlocks, stars, achievements, statistics and settings. Rename/avatar changes, confirmed deletion and JSON export/import are available. Imports always create separate local copies. Existing unreadable/future saves remain untouched and display an error. Device-storage failures display a backup warning. Stale tabs detect a changed device save and stop before overwriting it, offering an export/reload conflict path. Battles restart rather than save an in-flight combat snapshot; permanent rewards checkpoint on each completed wave.

Guest saves live in localStorage. Google is optional and for a parent/guardian; children need no account. Profile selection is not authentication: children sharing the parent login can switch profiles. A signed-in parent can review guest imports as a new hero, conservative merge, or backed-up replacement. Merge uses the higher lifetime Crown total minus the cost of all combined tower unlocks, rather than adding or replenishing balances; combines completed maps/stars/unlocks; accounts for XP already spent. It rejects combinations that cannot be reconciled safely. Guest originals remain local. Export omits other signed-out parents' cached profiles.

Cloud profiles use stable UUIDs at `users/{uid}/profiles/{profileId}` with schema 1. XP uses ten flat earned/spent integer fields on the Firestore wire to keep rule evaluation bounded; local profiles retain the readable five-class earned/spent objects. The loader supports both representations. A local durable queue records intent. Each Firestore transaction reads current cloud state, applies idempotent reward IDs and validates purchases against current balances. Concurrent duplicate rewards/unlocks never add currency twice or spend twice. Explicit replacement/merge checks the reviewed revision. Deleted cloud heroes are not silently resurrected. Sync conflicts retain the local queue and offer export/retry or export/use-cloud. Writes use `serverTimestamp()`. Reads occur on sign-in, focus, explicit refresh; writes occur after meaningful checkpoints/purchases. No per-frame reads/listeners, paid functions, billing, analytics, Storage or Firebase Hosting are configured. The bounded ledger stops with an export warning rather than discarding reward history. Rules protect ownership/schema, not hack-proof client-side currency.

## Firebase release contract

Client config comes verbatim from the verified issue #2 handoff, project `tiny-siege-game`, Standard default Firestore database `us-central1`, Spark/no billing. Only Google is enabled. Public API keys identify the app; ownership rules provide access control. No credentials are committed.

`firestore.rules` hardens the handed-off schema with exact fields, all nested XP/path types, enumerated IDs, bounded reward ledger/counters, owner-only CRUD/list and fresh server timestamps on both create and update. `firebase.json` contains only Firestore rules and local emulator configuration. It cannot deploy Firebase Hosting or enable billing. The authenticated administrator published the exact tested rules from commit `60630084e557299cb042e27e5371eaee53c2198b` on October 13, 2026 and read back the active version. [Deployment confirmation](https://github.com/m87dv9yywz-oss/tiny-siege/pull/4#issuecomment-6154165514) records matching Git blob `f6b73a73af96316de646bdf5717af688eef5a818`. Only rules changed; Spark, player data and authentication providers remain unchanged. No further Firebase administration action is required for this release.

Google popup sign-in starts directly from a user click after SDK loading. Cross-domain redirect is deliberately unused because GitHub Pages cannot provide the required reverse proxy for Safari storage restrictions. A home-screen popup fallback opens the normal browser tab; local export/import remains available. No additional provider is enabled. Auth/Firestore emulators validate Google credentials and independent browser clients, but real Google consent and physical iPhone Safari/home-screen authentication are still hardware/account acceptance checks. Do not claim they were performed.

## Validation

`npm test`: legacy combat and progression checks. `npm run test:browser`: all seven phone/tablet/desktop viewports, artwork, touch tap/drag, panel dismissal/range mode, controls, profiles, reload saves, maps and icons. `npm run test:cloud`: actual Firestore rules and Auth emulators plus multi-browser guest migration, convergence and offline/reconnect. The emulator project is `demo-tiny-siege`, isolated from production; only an explicit `?emulators` in a development build enables it. `npm run build` and `node scripts/production-smoke.js <preview-or-live-url>` exercise the shipped app without development hooks.

Local Firestore emulator download is denied by the managed workspace policy (`storage.googleapis.com`); GitHub Actions runs the required emulator checks in its ordinary CI environment. Test build gates deployment, and post-deploy CI verifies the public Pages URL. V3 should remain in its feature PR until these checks and the production rules deployment are complete. No physical device testing or universal 60-FPS claim is made; bounded effects and Canvas stress coverage are preserved.
